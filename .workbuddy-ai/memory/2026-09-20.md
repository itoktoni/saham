## Lanjutan — penarikan data otomatis (revisi ketiga)

Permintaan pengguna: jangan input manual, cari API data untuk menghitung semua metrik.

**Deliverable baru:** `D:\saham\fetch-data-idx.py` (~28 KB, hanya pustaka standar Python: `urllib`, `http.cookiejar`, `subprocess`, `csv`, `json`). Menulis `data-idx.csv` + `data-idx.json` persis dalam format `CSV_HEADER` screener, jadi bisa langsung diimpor.

**Sumber data yang dipakai:**
- IDX `https://www.idx.co.id/primary/ListedCompany/GetCompanyProfiles?start=0&length=1000` — nama & sektor resmi 962 emiten, tanpa API key. **Harus satu request `length=1000`**; `length=500` mengembalikan 404.
- Yahoo Finance `query1.finance.yahoo.com` — `/v8/finance/chart` (harga + riwayat 6 bulan untuk sinyal swing) dan `/v10/finance/quoteSummary` (EPS, BVPS, saham beredar, DER, arus kas).

**Kendala yang ditemukan (penting, jangan diulang):**
- **Tidak ada API gratis yang bisa dipanggil langsung dari browser.** Yahoo dan IDX sama-sama tidak mengirim header CORS, dan IDX di belakang Cloudflare. Jadi auto-fetch **wajib skrip lokal**, bukan `fetch()` di dalam halaman.
- **Cloudflare memblokir berdasarkan TLS fingerprint, bukan User-Agent.** `urllib` dapat 403/404 dari IDX sementara `curl` dapat 200. Solusi: transport ganda — `urllib` dulu, jatuh ke `curl` via `subprocess` bila gagal.
- **Yahoo butuh cookie + crumb.** Alur: ambil cookie dari `fc.yahoo.com`, lalu `/v1/test/getcrumb`. Crumb kedaluwarsa → 401 `Invalid Crumb`; tangani dengan login ulang otomatis pada 401/403.
- **Rate limit 429** bila beberapa `quoteSummary` ditembak cepat. Tangani dengan backoff bertambah (15s x percobaan) + opsi CLI `--delay` (default 1,5s).
- **Yahoo tidak punya laporan kuartalan untuk emiten IDX.** `balanceSheetHistoryQuarterly` dan `cashflowStatementHistoryQuarterly` praktis kosong (hanya `endDate`), dan `financialData` tidak punya `freeCashflow`/`debtToEquity`. Jadi `ekuitas` **diturunkan** dari `bookValue` × `sharesOutstanding`.
- **`s_topbuyer` tidak tersedia di sumber gratis mana pun** — harus diisi manual dari broker summary.
- **Data emiten kecil di Yahoo sering salah** (KRAS `bookValue` 0,035; MEJA `trailingEps` kosong). Tidak diperbaiki, tapi **divalidasi**: `build_record()` menyusun daftar masalah dan menulis label kualitas ke kolom `sumber` → "kualitas baik" / "perlu dicek: ..." / "data meragukan (N masalah)". Validator ini bekerja sebagaimana mestinya (menangkap PBV ADRO 16.500x yang memang tidak wajar).

**Bug nyata yang ditemukan lewat uji otomatis (jangan sampai terulang):**
1. **BOM merusak kolom pertama.** Skrip menulis CSV dengan `utf-8-sig`, sehingga header pertama menjadi `\ufeffkode` dan **seluruh baris akan terbuang diam-diam** karena `kode` tidak ditemukan. Perbaikan: buang BOM sebelum parsing.
2. **Titik desimal dibaca sebagai pemisah ribuan.** Pembaca lama melakukan `.replace(/\./g,"")` dengan asumsi gaya Indonesia, sehingga `0.1924` menjadi `1924` — DER meleset 10.000x. Perbaikan: fungsi `toNum()` yang sadar format — koma = desimal (gaya Indonesia), titik = desimal kecuali polanya jelas bergrup (`1.234.567`). Angka diekstrak dengan regex, **bukan** dengan membuang karakter, supaya huruf "e" pada kata seperti "DER" tidak terbaca sebagai notasi eksponen.
3. **Sektor IDX-IC salah dipetakan.** IDX-IC memakai "Barang Konsumen Non-Primer", bukan "Konsumen Non-Primer", sehingga sektor jatuh ke nilai mentah dan ditolak screener (MEJA jadi "Energi"). Sekaligus menambah sektor **Teknologi** yang belum ada di daftar screener.
4. **Cache menyimpan hasil pemetaan yang sudah jadi**, jadi perbaikan `SEKTOR_MAP` tidak berlaku sampai cache kedaluwarsa 7 hari. Perbaikan: petakan ulang saat cache dibaca (idempoten).

**Perubahan di sisi HTML:** tombol menjadi **Import CSV/JSON** (sebelumnya "Import CSV"); importer mendeteksi JSON otomatis; `mapStock()` dipakai bersama CSV & JSON; `normSektor()` + `SEKTOR_ALIAS` menerima nama IDX-IC/Inggris; panduan bagian G ditulis ulang menjadi G.1 (cara pakai skrip) / G.2 (batas data otomatis) / G.3 (format berkas + aturan titik-koma).

**Kolom "Mutu data" (temuan uji terakhir):** label kualitas dari kolom `sumber` ternyata **diimpor tapi tidak pernah ditampilkan** — pengguna tidak bisa tahu baris mana yang datanya meragukan, padahal itu inti dari validasi fetcher. Ditambahkan `sumberTag()` yang memetakan catatan menjadi label berwarna: hijau "Baik" / amber "Perlu dicek" / merah "Meragukan" / abu "Manual", dengan catatan lengkap di tooltip. Rincian 7 langkah (`openDetail`) juga menampilkan blok "Asal data & mutu" — memakai gaya peringatan bila datanya meragukan.

**Verifikasi:** 31 tes impor + 40 tes smoke lulus (harness DOM tiruan + `node --check`), mencakup impor CSV & JSON nyata, 6 sektor valid, 14 kasus pembaca angka, label mutu data, panel rincian, dan pipeline penuh tanpa NaN. Contoh keluaran disimpan sebagai `contoh-data-idx.csv` / `.json`; cache IDX di `idx-profil.json`. Ukuran HTML 124,1 KB.

## Lanjutan — stepper 7 langkah + panduan per langkah + regime pasar otomatis (revisi kelima)

Pengguna: *"masih terlalu susah ya, buatkan step by step nya mungkin dengan collapse atau stepper … bagaimana cara mendapatkan datanya? atau datanya itu otomatis? terus bagaimana cara melihat indikatornya kita bahas 1 per 1 dari langkah 1"*. Intinya tiga hal: (1) alat terasa terlalu rumit, (2) perlu kejelasan data mana otomatis dan mana manual, (3) perlu penjelasan cara membaca indikator, mulai dari Langkah 1.

### Yang dibangun

**Stepper + lipat.** Bilah langkah bernomor (`s0`–`s7`) dengan penanda langkah aktif (scroll-spy), tombol **Buka semua** / **Tutup semua**, dan status kesiapan per langkah (`stepSiap()`): Langkah 1 butuh `pasar.json`, Langkah 2 ke atas butuh data emiten. Setiap kartu bisa dilipat lewat klik judulnya (`bindFold()` + `setFold()`), dengan penjaga agar klik pada `button/input/select/a` tidak ikut melipat.

**Panel panduan per langkah (`GUIDE` + `renderStepGuides()`).** Setiap langkah disisipi panel berisi dua bagian:
- **Tabel sumber data** — 4 kolom (indikator · jenis · asal · penjelasan). Kolom "jenis" memakai badge `srcBadge()`: **Otomatis** (hijau) / **Semi-otomatis** (kuning) / **Manual** (abu) / **Campuran** / **Referensi**.
- **"Cara membaca indikatornya"** — prosa per indikator. `GUIDE.s1` paling rinci (~2.400 char): tabel 4 kuadran, lalu 5 indikator satu per satu, lalu "hasil akhir langkah ini".

**Jawaban atas "otomatis atau tidak?" — dipetakan tegas per indikator Langkah 1:**
| Indikator | Jenis | Sumber |
|---|---|---|
| Kuadran siklus | **Otomatis** | riwayat IHSG 1 tahun (Yahoo `^JKSE`) |
| Tren likuiditas | **Otomatis** | nilai transaksi harian IDX vs rata-rata 30 hari |
| Kekuatan sektor | **Semi-otomatis** | agregasi return 6 bulan emiten yang sudah ditarik |
| BI Rate | **Manual** | situs BI |
| Toleransi risiko | **Manual** | selera pengguna |

### Penemuan teknis penting

- **Indeks sektor IDX tidak tersedia gratis.** Yahoo mengembalikan **1 titik data** untuk `IDXENERGY.JK` (tak terpakai), dan `IDXENERGY` tanpa sufiks tidak mengembalikan apa pun. Endpoint `GetIndexSummary` hanya memuat 10 indeks lebar (COMPOSITE, LQ45, IDX30, IDX80, IDXESGL, IDXQ30, IDXV30, IDXG30, IDXHIDIV20, IDXLQ45LCL) — **tanpa indeks sektor**. Karena itu kekuatan sektor dihitung dari agregasi return emiten, dan UI menyatakan terang-terangan *"bukan indeks sektor resmi"*.
- **`^JKSE`, `^JKLQ45`, `^JKII` punya riwayat nyata** (240 bar/1 tahun) bila `fetch_chart` dipanggil dengan `suffix=""`. Ini membuka jalan regime makro otomatis.
- **Nilai transaksi harian ada di `GetIndexSummary`**, baris `COMPOSITE`, kolom `Value` — inilah indikator likuiditas yang selama ini hilang. Mendukung `?date=YYYYMMDD` sehingga bisa dirata-ratakan mundur per hari.
- **Urutan aturan kuadran** (yang akhirnya dipakai, diverifikasi terhadap data nyata):
  1. `r3 < −10%` **dan** di bawah MA50 → **Bust**
  2. `r3 < 0` **dan** di bawah MA50 → **Slowdown**
  3. `r3 > 0` **dan** jarak dari puncak > −8% → **Overheat**
  4. `r3 > 0` **dan** jarak dari puncak ≤ −8% → **Recovery**
  5. selain itu → **Slowdown**
- **Ambang likuiditas:** rasio ≥ 1,15 → Longgar · ≤ 0,85 → Ketat · selain itu Netral.
- **Target MOS mengikuti kuadran:** Recovery 25% · Overheat 30% · Slowdown 35% · Bust 40% (tidak diketahui → 30%).
- **`.mbar` adalah rel, bukan batang.** Harus berisi anak `<i>` sebagai pengisi: `<span class="mbar"><i style="width:X%"></i></span>`. Salah pakai membuat batang tidak tampil sama sekali.

## Catatan — akses data IDX: login TIDAK diperlukan (diverifikasi)

Pengguna menawarkan akun idx.co.id-nya. Sebelum memakai apa pun, endpoint publik diuji langsung untuk memastikan apakah akun itu memang dibutuhkan. **Kesimpulan: tidak.** Kredensial tidak dipakai, tidak disimpan, dan tidak dituliskan ke berkas mana pun.

**Hasil uji endpoint (tanpa login sama sekali):**

| Endpoint | Hasil | Catatan |
|---|---|---|
| `ListedCompany/GetCompanyProfiles` | **HTTP 200** | 962 emiten, terisi lengkap |
| `TradingSummary/GetIndexSummary` | **HTTP 200** | 10 baris indeks; COMPOSITE Close 6441,159 |
| `ListedCompany/GetFinancialReport` | **HTTP 200** | Endpoint terbuka, tetapi kombinasi parameter belum ketemu (`ResultCount: 0`) |

**Temuan penting soal Cloudflare:** server IDX menolak `urllib` Python dengan **HTTP 403** karena sidik jari TLS-nya, tetapi **menerima `curl`** dengan User-Agent peramban. Inilah alasan `fetch-data-idx.py` punya transport cadangan `_curl_get()`. Jangan hapus jalur curl itu — tanpanya seluruh penarikan IDX gagal. Menembak endpoint bertubi-tubi memicu rate-limit (halaman tantangan *"Just a moment..."*), jadi beri jeda ≥3 detik.

**Peluang yang belum digarap:** bila `GetFinancialReport` berhasil dipetakan parameternya, **laporan keuangan IDX bisa ditarik otomatis** — ini berpotensi menggantikan salin-tempel manual dari Stockbit untuk laba 10 tahun, neraca, dan arus kas (utang teknis `fcf`/`kas`/`utang`). Parameter yang sudah dicoba dan gagal: `reportType=rda` dengan `indexFrom/indexTo`, `year`, `kodeEmiten`, `emitenType=s`, `periode=Audited`. Berikutnya: telusuri berkas JS halaman IDX untuk melihat bentuk panggilan sebenarnya.

**Catatan keamanan:** pengguna mengirim username & password di dalam percakapan. Sudah disarankan mengganti password dan mengaktifkan verifikasi dua langkah. Kredensial **tidak** dicatat di berkas memori ini maupun berkas proyek mana pun.

## Lanjutan — penarikan laporan keuangan IDX otomatis (revisi keenam)

Tindak lanjut dari temuan bahwa login IDX tidak diperlukan: pengguna setuju bahwa data laporan keuangan otomatis akan jauh lebih baik. Targetnya menutup utang teknis terbesar — laba, ekuitas, arus kas, kas, dan utang yang selama ini **diturunkan dari Yahoo** atau harus **disalin-tempel manual dari Stockbit**.

### Cara kerja (semuanya tanpa login)

1. `GET /primary/ListedCompany/GetFinancialReport?kodeEmiten=&year=&periode=audit&pageSize=100&reportType=rdf` → metadata + daftar lampiran.
2. Unduh lampiran **`.xlsx`** (XBRL) — di dalamnya ada neraca, laba rugi, arus kas.
3. Baca sheet **berdasarkan judul**, bukan kode sheet.

**Kunci parameternya adalah `reportType=rdf` dan `periode=audit`** — bukan `rda` yang saya coba lebih dulu (itu yang membuat `ResultCount: 0` selama beberapa percobaan). Nilai `periode` lain: `TW1`, `TW2`, `TW3`.

### Jebakan yang ditemukan (semuanya nyata, semuanya sudah ditangani)

- **Kode sheet berbeda per template industri.** Bank memakai `4220000`/`4322000`/`4510000`; infrastruktur memakai `3210000`/`3312000`/`3510000`. Karena itu sheet **wajib dikenali dari judulnya** ("Statement of financial position" / "profit or loss" / "cash flows"). Menghafal kode = rusak pada industri lain.
- **Setiap sheet memuat kolom tahun berjalan DAN tahun sebelumnya**, jadi satu berkas memberi dua tahun.
- **Label "Pembulatan" IDX tidak bisa dipercaya antar tahun.** Contoh nyata: BBCA 2022 & 2024 dalam jutaan (total aset 1.314.731.674), tetapi **2023 dalam rupiah penuh** (1.408.107.010.000.000) — padahal label ketiga berkas sama-sama "Jutaan / In Million". Diperbaiki lewat `selaraskan_skala()`: kelas besaran (pangkat 1000) total aset dihitung per tahun, kelas yang **paling banyak muncul** dijadikan acuan, tahun lain diselaraskan ke situ, lalu satuan akhir mengikuti skala yang dideklarasikan.
- **Laba induk ≠ laba total.** `Jumlah laba (rugi)` sudah termasuk kepentingan non-pengendali. Yang benar dipakai adalah **`Laba (rugi) yang dapat diatribusikan ke entitas induk`**, karena hanya itu yang konsisten dengan EPS. Pada TLKM 2024 bedanya besar: 30.743 vs 23.649 miliar, sedangkan EPS 238,73 × 99,06 miliar saham = 23,65 T. Salah pilih = PER tampak 23% lebih murah.
- **Sebagian berkas `.xlsx` rusak di sisi IDX sendiri.** ANTM 2024: server membalas **HTTP 200 dengan content-type xlsx**, tetapi isinya hanya kata "Administrator" berulang (165 byte). Ini **bukan** blokir Cloudflare. Karena itu ada `_xlsx_sah()` yang memeriksa **isi** berkas (harus diawali `PK`, karena xlsx = arsip ZIP) — bukan sekadar ukurannya. Berkas rusak yang tertulis ke disk akan terlihat "ada" dan bisa dipakai sebagai laporan palsu.
- **Ada cadangan: `inlineXBRL.zip`.** Berisi HTML per bagian laporan dengan struktur setara (label di kolom kiri, nilai di kolom kanan) — dan lebih baik lagi, tiap nilai membawa atribut **`scale`** (mis. `scale="6"` = jutaan) sehingga skala terbaca pasti, bukan dari label yang bisa keliru. Terbukti menyelamatkan ANTM 2024 (laba 3,65 T / aset 44,52 T, konsisten dengan 2023: 3,08 T / 42,85 T).
- **`hist_laba` sempat terbuang.** `CSV_HEADER` di Python hanya memuat 31 kolom inti, sedangkan screener mengharapkan 43. 12 kolom tambahan ditambahkan **di akhir** sesuai konvensi kontrak. `hist_laba` satuannya **MILIAR rupiah** (sesuai `chartLaba` di screener).
- **Catatan mutu lama bisa jadi tidak berlaku.** Yahoo menandai BBCA "arus kas operasi negatif (lazim tidak akurat untuk bank)"; setelah arus kas **asli** IDX masuk (positif 53,8 T), catatan itu dibatalkan otomatis dan diganti keterangan bahwa laporan IDX yang membatalkannya.

### Yang dibangun

- Kelas `LaporanIDX` + `selaraskan_skala()` + `gabung_laporan()` di `fetch-data-idx.py`.
- Argumen baru: `--laporan` (gabungkan ke data Yahoo), `--laporan-saja` (hanya laporan IDX, jauh lebih cepat), `--laporan-tahun 2015-2024` (bawaan: 10 tahun terakhir), `--laporan-delay`.
- Cache berkas di `cache-laporan/`, keluaran `laporan-idx.json`.
- `gabung_laporan()` **menimpa** nilai turunan Yahoo dengan angka asli IDX: `ekuitas`, `laba`, `eps`, `kuartal` (=4), `fcf` (=arus kas operasi), `kas`, `utang` (=total liabilitas), `der` (gaya Indonesia: liabilitas/ekuitas), `sektor` (dari IDX-IC, lebih otoritatif), dan `hist_laba` 10 tahun. Plus verifikasi silang EPS × saham vs laba induk.
- `GUIDE.s2` di screener ditulis ulang (1.537 → 3.185 char): dua jalur otomatis, jebakan skala, dan penjelasan laba induk vs laba total.

### Batas yang diketahui

- Emiten kecil / laporan lama bisa tidak punya lampiran `.xlsx` maupun `inlineXBRL.zip`.
- Cloudflare membatasi berkas statis; jeda bawaan 1.5 s per tahun per emiten. 10 tahun × 8 emiten ≈ 6–8 menit.
- `instance.zip` (XBRL mentah, mis. 3,7 MB `instance.xbrl`) belum diparse — cadangan terakhir bila `inlineXBRL` pun tidak ada.
- F-Score, Altman Z, dan sebagian rasio siap pakai tetap hanya ada di jalur tempel Stockbit.

### Koreksi penting — pendekatan penyelarasan skala (percobaan pertama salah)

Percobaan pertama menyelaraskan skala **dari data mentah** (kelas besaran aset mentah → mayoritas → acuan). Ini **gagal** pada ANTM 2020: aset mentah 31.729.512.995 (3,17e10) membuat `round(log10/3)` = `round(3,5)` = **4** (pembulatan bankir), sedangkan 2019 yang besarnya nyaris sama (3,02e10) dapat kelas **3**. Karena tahun 2021-2024 semuanya di kelas 3 (mentah ~3,3e7), acuannya jadi 3 dan 2020 "dikoreksi" ke bawah 1000x — padahal label IDX untuk 2020 ("Ribuan") sudah **benar**.

**Pelajaran: kelas besaran data mentah tidak boleh dipakai sebagai acuan, karena nilainya bisa jatuh tepat di batas pembulatan.**

Pendekatan yang benar (dipakai sekarang) — **dua tahap, urutannya penting**:
1. **Percayai label 'Pembulatan' tiap tahun.** Pada mayoritas kasus label itu benar.
2. **Baru deteksi penyimpangan** dari hasil yang sudah berskala: bandingkan total aset tiap tahun dengan acuan (kelas besaran terbanyak, lalu median di dalam kelas itu); geser tahun yang menyimpang sejauh ≥ pangkat 1000.

Tahap 1 saja tidak cukup (BBCA 2023 salah). Tahap 2 saja juga tidak cukup (ANTM 2020 salah). Keduanya diperlukan.

## Fase 8 — Verifikasi impor menemukan 3 bug nyata (bukan nol)

Uji impor CSV 43 kolom lulus, tetapi justru memunculkan tiga cacat asli. Semuanya diperbaiki dan dikunci dengan tes.

### Bug 1 — `eps_trend` basi, tidak dihitung dari riwayat laba IDX

`gabung_laporan()` menimpa ekuitas/laba/eps/fcf/kas/utang/der/sektor/hist_laba, tetapi **tidak** menyentuh `eps_trend`. Kolom itu tetap dari Yahoo/tempelan manual, padahal bobotnya paling besar di peringkat (tier 1/200/1000 poin). Akibatnya ASII -- labanya 21,7 T (2019) -> 34,1 T (2024), tumbuh jelas -- tertulis **"down"** dan terlempar ke peringkat **terakhir** meski satu-satunya emiten yang lolos 5/5 kriteria. BBCA juga salah ("fluktuatif" padahal 28,6 -> 54,8 T).

Perbaikan: `tren_laba(hist)` + `AMBANG_TREN = 0.05` di `fetch-data-idx.py`, dipanggil dari `gabung_laporan()`. Kembarannya `trenDariHist(hist)` + `AMBANG_TREN` di screener, dipakai `mapStock()` **hanya bila** kolom `eps_trend` kosong (isi eksplisit tetap dihormati).

Metode: **regresi linear pada laba yang dinormalkan** terhadap laba tipikal (rata-rata nilai absolut). Kemiringan terbaca sebagai "berapa persen dari laba tipikal per tahun", tidak bergantung skala, dan **tetap bekerja walau ada tahun merugi** -- beda dengan regresi log-linear yang tidak terdefinisi untuk laba <= 0. Minimal 4 titik; kurang dari itu kembalikan None/"" supaya tidak menebak.

Hasil: BBCA fluktuatif->up (+0,152), TLKM up->fluktuatif (+0,041), ANTM up (+0,312), ASII down->up (+0,137).
Peringkat berubah: **ASII 4 -> 1** (total 1008 -> 9).

### Bug 2 — `parseCsv` memakai koma DAN titik koma sekaligus

`parseCsv` memperlakukan `,` dan `;` sama-sama sebagai pemisah. Begitu satu titik koma muncul di kolom bebas (`sumber`), seluruh kolom sesudahnya bergeser satu: `div_yield` jadi 0 dan `hist_laba` hilang **tanpa peringatan**. Ini muncul persis saat catatan "tren laba dikoreksi IDX: ... -> ..." ditambahkan ke `sumber`.

Dua sisi diperbaiki:
- **Screener**: `pemisahCsv(text)` mendeteksi pemisah **sekali** dari baris judul (titik koma menang bila lebih banyak dari koma, dengan menghormati tanda kutip). `parseCsv` memakai satu pemisah itu saja.
- **Python**: `bidang_csv()` + `tulis_csv()` menggantikan `csv.DictWriter`. `QUOTE_MINIMAL` hanya mengutip koma, **bukan titik koma**, jadi penulis CSV ditulis tangan agar kutipannya kembar dengan `csvLine()` di screener. `import csv` dihapus (tidak lagi terpakai).

Tambahan pencegahan: `importCsv` sekarang menghitung baris yang jumlah kolomnya tidak sama dengan judul dan memberitahukannya lewat toast, alih-alih menerimanya diam-diam. `applyImport(list, catatan)` menerima pesan tambahan.

### Bug 3 — ambang likuiditas berbeda antara filter dan tier

`likuidSkor()`/`likuidLabel()` dipatok `10e9`, sedangkan filter Langkah 3 memakai `S.cfg.thr.minNilai` = `5e9`. Emiten dengan nilai transaksi Rp7 M **lolos filter** tetapi tetap dicap "Tidak Likuid" dan dapat 1000 poin, terlempar ke bawah tanpa alasan yang terlihat. Sekarang keduanya memakai `S.cfg.thr.minNilai`.

### Sisa pertanyaan desain (belum diubah, menunggu keputusan pengguna)

Skor tier `likuidSkor` (1/1000) dan `EPS_TREND_SKOR` (1/200/1000) jauh lebih besar daripada jumlah peringkat (maks 4 x 4 = 16). Jadi peringkat sebenarnya **diurutkan oleh tier dulu**, bukan oleh jumlah peringkat seperti yang tertulis di dokumen (dokumen menyebut `Rank_Likuiditas` dan `Rank_EPS Trend` sebagai *rank* 1..N). Setelah Bug 1 diperbaiki, TLKM (+4,1%/tahun) jatuh ke peringkat 4 semata karena tier "fluktuatif" = 200, padahal jumlah peringkatnya (9) lebih baik daripada BBCA dan ANTM (12). Opsi: (a) biarkan sebagai bias sengaja anti-downtrend, (b) jadikan rank 1..N agar sama dengan dokumen, (c) kecilkan bobot tier jadi tie-breaker (mis. 1/2/3).

Catatan kecil: BBCA dan ANTM seri di total 14; pemecah serinya adalah urutan masukan (sort stabil), jadi belum deterministik secara makna.

## Fase 9 — Uji ulang Cloudflare: tidak butuh Playwright/browser

Pertanyaan pengguna: apakah perlu Playwright atau browser lain untuk melewati Cloudflare? Jawabannya **tidak**. Diuji langsung 2026-09-20 dengan empat percobaan pada URL yang sama, header sama, UA sama, mesin sama:

| Perlakuan | Hasil |
|---|---|
| `curl`, tanpa cookie, lampiran `/Portals/0/...xlsx` | **HTTP 403**, 6.621 byte HTML, header `Cf-Mitigated: challenge` |
| `curl`, pemanasan halaman utama dulu (jar cookie) | **HTTP 200**, 225.497 byte, `PK\x03\x04` (ZIP sah) |
| `curl`, tanpa cookie, endpoint API JSON | **HTTP 200**, 5.621 byte JSON |
| `urllib` (stdlib Python), UA Chrome lengkap + Referer + Accept | **HTTP 403**, `Just a moment...`, cf-ray SIN |

**Kesimpulan:**
1. Yang diblokir **bukan** JavaScript challenge, melainkan **ketiadaan cookie sesi Cloudflare**. Satu GET ke halaman utama sudah cukup — tidak ada teka-teki JS yang perlu dieksekusi, jadi browser headless tidak diperlukan.
2. Perbedaan `curl` vs `urllib` murni **sidik jari TLS/HTTP**, bukan header. Karena `requests`/`httpx` memakai tumpukan OpenSSL yang sama dengan `urllib`, keduanya akan kena 403 juga. `curl` adalah transport yang harus dipertahankan.
3. **Endpoint API JSON tidak seketat berkas statis.** `/primary/ListedCompany/...` balas 200 tanpa cookie; `/Portals/0/...` selalu lewat managed challenge. Jadi pemanasan hanya wajib untuk unduhan lampiran.
4. Angka 6.621 byte itu cocok dengan pengamatan lama (165 byte / 6.621 byte) — memang halaman tantangan, dan `_xlsx_sah()` menangkapnya lewat pemeriksaan magic bytes `PK`.

### Perbaikan yang dipicu temuan ini

`pemanasan()` dulu **selalu** mengembalikan `True` tanpa memeriksa apa pun — jadi kegagalan pemanasan baru ketahuan jauh di hilir sebagai "laporan tidak bisa dibaca". Sekarang:
- `ada_cookie_sesi()` memeriksa berkas jar benar-benar memuat `__cf_bm` atau `auth.strategy`.
- `pemanasan(log_fn, percobaan_maks=3)` mengulang dengan jeda makin lama (2 s, 4 s), lalu jujur mengembalikan `False`.
- Pemanggil di `main()` memberi tahu pengguna bahwa berkas statis kemungkinan dibalas HTTP 403 dan menyarankan mencoba lagi nanti.

Diuji hidup: `pemanasan()` -> True, cookie terdeteksi, `satu_tahun("BBCA", 2024)` -> laba 5,4836e7 (satuan juta) / ekuitas 2,6284e8 / aset 1,4493e9, berkas cache `BBCA-2024.xlsx` terbentuk.
